# Changelog

Version 7.0.0 reshapes reading and writing in one step, without a deprecation
phase. Consumers write through two operations, `set_feature` and
`run_command`, and learn about a failed write through one exception. How a
command is sent is internal to the library. The design decisions are recorded
in [ADR 0005](https://github.com/ignazhabibi/vi_api_client/blob/main/docs/adr/0005-keep-command-knowledge-in-the-library.md).

### Breaking Changes 🚨
- `7f5c777` Availability is one concept and the read methods share their parameters. `Feature.is_available` and `Feature.is_settable` are new. `only_enabled` is renamed to `only_available` on `get_features`, `refresh_device`, and `get_full_installation_status` and defaults to `True` on all three, so `get_features` no longer returns disabled or not-ready features unless the caller passes `only_available=False`. `get_devices` loses `include_features` and returns devices without features. `GatewayDeviceRefreshResult.updated_devices` is renamed to `refreshed_devices` ([#202](https://github.com/ignazhabibi/vi_api_client/pull/202)).
- `1a01578` The models are plain data classes. The `from_api` classmethods are removed; API responses are parsed inside the library ([#203](https://github.com/ignazhabibi/vi_api_client/pull/203)).
- `8bd36fe` `FeatureConstraints` replaces `FeatureControl`, and `Feature.constraints` replaces `Feature.control`. The constraints hold only the rules for writing a value (`value_type`, `min`, `max`, `step`, `options`, `min_length`, `max_length`, `pattern`, `schedule`). Command names, parameter names, required parameters, and URIs leave the public model, so a hand-built feature is read-only. The CLI `get-feature --json` document replaces the key `control` with `constraints` and `command` and prints no command URI ([#204](https://github.com/ignazhabibi/vi_api_client/pull/204)).
- `ce725cb` `set_feature` returns only the command-updated `Device` and accepts a `Feature` or a feature name. `execute_command` and `CommandResponse` are removed; `run_command(device, api_feature_name, command_name, parameters)` runs any command an API feature reports. A rejected command raises the new `ViCommandRejectedError` instead of returning a response object. Every error response with the error type `DEVICE_COMMUNICATION_ERROR` raises the new `ViDeviceCommunicationError` instead of `ViValidationError` or `ViServerInternalError`. The CLI `exec` command takes an API feature name instead of a flat feature name and accepts any reported command ([#205](https://github.com/ignazhabibi/vi_api_client/pull/205)).
- `0095c91` `set_feature` writes boolean features whose device offers only an on/off command pair, such as `enable` and `disable` for `heating.dhw.hygiene.enabled`. These features change from read-only to writable; the list is below ([#206](https://github.com/ignazhabibi/vi_api_client/pull/206)).
- `9f6aa10` Only a command whose name starts with `set` binds a value to a feature. Features that `schedule`, `activate(begin, end)`, or `triggerDaily` wrote change from writable to read-only, because those commands do more than store a value; the list is below. Their commands are sent with `run_command` ([#207](https://github.com/ignazhabibi/vi_api_client/pull/207)).

#### Migration

| Before | After |
| --- | --- |
| `response, device = await client.set_feature(device, feature, value)` and `if not response.success` | `device = await client.set_feature(device, feature, value)` and `except ViCommandRejectedError` |
| `await client.execute_command(feature, parameters)` | `await client.run_command(device, api_feature_name, command_name, parameters)` |
| `feature.control.min` | `feature.constraints.min` |
| `feature.is_writable and feature.is_enabled and feature.is_ready` | `feature.is_settable` |
| `result.updated_devices` | `result.refreshed_devices` |
| `only_enabled=...` | `only_available=...`; check call sites that relied on the old default |
| `get_devices(..., include_features=True)` | `get_devices(...)` then `refresh_gateway_devices(devices)` |
| `Device.from_api(...)` | read through the client or `FixtureViClient` |
| `get_features(device)` returned disabled and not-ready features by default | pass `only_available=False` to get them |
| `set_feature` on holiday dates, daylight saving dates, or hygiene trigger times | `run_command` with `schedule`, `activate`, or `triggerDaily` / `triggerOncePerWeek` and all their parameters |
| `except ViValidationError` for an unreachable device or gateway | `except ViDeviceCommunicationError` |
| hand-built writable `Feature(..., control=FeatureControl(...))` | take a writable feature from a client read and adjust it with `dataclasses.replace` |
| CLI `get-feature --json` key `control` (with command URI) | keys `constraints` and `command`, no URI |
| CLI `exec <flat feature name> <command>` | `exec <API feature name> <command>`; any reported command is allowed |

`run_command` needs a device snapshot from `refresh_device`,
`refresh_gateway_devices`, or `get_full_installation_status`, because only
those carry the list of reported commands.

#### Features that become writable through an on/off command pair

The pairs come from an explicit table: the one-time charge, hygiene, the
heating programs `comfort`, `eco`, and `forcedLastFromSchedule`, and the
ventilation quick modes. A parameter setter such as `setEnabled` always wins,
so no feature that was writable before is written with a different command.
In the bundled fixtures:

| Fixture | Features that become writable |
| --- | --- |
| Vitocal200S | `heating.circuits.0.operating.programs.comfort.active`, `heating.circuits.0.operating.programs.eco.active`, and the same two on circuit 1 |
| Vitocal222S | `heating.circuits.0.operating.programs.forcedLastFromSchedule.active`, `heating.dhw.hygiene.enabled` |
| Vitocal250A | `heating.circuits.0.operating.programs.forcedLastFromSchedule.active` |
| Vitocal333G-with-Vitovent300F | `heating.circuits.0.operating.programs.comfort.active`, `heating.circuits.0.operating.programs.eco.active`, and the same two on circuit 1; `ventilation.quickmodes.comfort.active`, `ventilation.quickmodes.eco.active` |
| Vitocharge03 | none |
| Vitodens200W | `heating.circuits.0.operating.programs.comfort.active`, `heating.circuits.0.operating.programs.forcedLastFromSchedule.active`, `heating.dhw.hygiene.enabled` |
| Vitopure350 | `ventilation.quickmodes.forcedLevelFour.active`, `ventilation.quickmodes.silent.active` |

Whether the API reports a pair as executable does not decide writability, so
a feature does not switch between writable and read-only as the device state
changes. The API decides whether a write is allowed; a command it does not
allow raises `ViCommandRejectedError`. A device can report a pair it never
allows: Vitodens200W reports both `comfort` commands as not executable, so
writing that feature may fail on every attempt.

#### Features that stop being writable under the setter rule

| Fixture | Features that stop being writable |
| --- | --- |
| Vitocal200S | `heating.operating.programs.holiday.start`, `.end` |
| Vitocal222S | `device.time.daylightSaving.begin`, `.end`; `heating.operating.programs.holiday.start`, `.end`; `heating.operating.programs.holidayAtHome.start`, `.end` |
| Vitocal250A | `heating.operating.programs.holiday.start`, `.end`; `heating.operating.programs.holidayAtHome.start`, `.end` |
| Vitocal333G-with-Vitovent300F | `heating.operating.programs.holiday.start`, `.end`; `ventilation.quickmodes.holiday.start`, `.end` |
| Vitocharge03 | `device.time.daylightSaving.begin`, `.end` |
| Vitodens200W | `device.time.daylightSaving.begin`, `.end`; `heating.dhw.hygiene.trigger.startHour`, `.startMinute`; `heating.operating.programs.holiday.start`, `.end`; `heating.operating.programs.holidayAtHome.start`, `.end` |
| Vitopure350 | none |

Two consequences:

- On Vitocal250A the daylight saving dates stay writable and are now written
  through `setActive` instead of `activate`, because that device reports the
  setter.
- Vitocharge03 has no writable feature left, because its only commands are
  `activate` and `deactivate` on `device.time.daylightSaving`.

A holiday is planned with `run_command`:

```python
await client.run_command(
    device,
    "heating.operating.programs.holiday",
    "schedule",
    {"start": "2026-12-24", "end": "2026-12-31"},
)
```

### New Features 💫
- `8bd36fe` `Device.get_command_names(api_feature_name)` lists every command an API feature reports, including commands that write no feature ([#204](https://github.com/ignazhabibi/vi_api_client/pull/204)).
- `ce725cb` The CLI `get-feature` command lists the commands of the feature's API feature with their parameters, required markers, and constraints. For error responses other than a rejected command, a text `extendedPayload.reason` such as `DEVICE_OFFLINE` is appended to the exception message ([#205](https://github.com/ignazhabibi/vi_api_client/pull/205)).
- `9ae3f64` `ViClient.get_event_history_window(installation_id, days, *, limit=None, max_pages=50)` follows the event history cursor across one lookback window and returns the new `EventHistoryWindow` with every event, the remaining cursor when the page safety limit stopped the traversal, and the number of pages fetched ([#208](https://github.com/ignazhabibi/vi_api_client/pull/208)).
- `64b8e7f` `Feature.deprecation` carries the removal notice Viessmann reports for an API feature as the new `FeatureDeprecation` with `removal_date` and `info`. The library only reports the notice: it does not act on it and does not map old feature names to new ones. The CLI `get-feature` command prints it in text and JSON ([#209](https://github.com/ignazhabibi/vi_api_client/pull/209)).
- `95d0c76` `vi-client list-features --deprecated` lists only features with a removal notice, each with its notice. `list-features --json --values` documents gain the key `deprecation` ([#210](https://github.com/ignazhabibi/vi_api_client/pull/210)).
